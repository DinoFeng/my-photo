
# 多队列多消费者架构 - 研究文档

## 1. 架构模式选择

### 1.1 消息队列模式对比

| 模式 | 描述 | 优点 | 缺点 |
|------|------|------|------|
| **点对点** | 一条消息被一个消费者消费 | 简单，负载均衡 | 不支持多播 |
| **发布/订阅** | 一条消息被多个消费者消费 | 支持多播 | 复杂，需要额外处理 |
| **多队列单类型** | 每种类型独立队列 | 隔离性好，易于扩展 | 需要管理多个队列 |

**决策**: 采用**多队列单类型**模式

**理由**:
- 隔离性好，不同类型任务互不影响
- 易于扩展，可独立调整每个队列的消费者数量
- 符合用户需求："一条队列只支持一种消息"

### 1.2 持久化方案选择

| 方案 | 描述 | 优点 | 缺点 |
|------|------|------|------|
| **文件存储** | 每个队列一个 JSON 文件 | 简单，无需额外依赖 | 并发写入不安全，查询效率低 |
| **SQLite** | 使用 SQLite 数据库存储 | 事务支持，查询高效 | 需要数据库操作 |

**决策**: 使用 **SQLite 数据库**

**理由**:
- 项目已使用 SQLite，无需引入新依赖
- 事务支持保证并发安全
- 查询效率高，支持索引

## 2. 关键技术实现

### 2.1 队列存储设计

```
任务队列表 (task_queue):
- id: 任务唯一标识 (UUID)
- type: 消息类型/队列名称
- payload: 任务参数 (JSON)
- status: 状态 (pending/running/done/failed)
- consumer_id: 当前处理的消费者ID
- retry_count: 已重试次数
- max_retries: 最大重试次数
- created_at: 创建时间
- updated_at: 更新时间
```

### 2.2 消费者模式

采用**轮询 + 乐观锁**模式：

1. 消费者定期轮询待处理任务
2. 使用 `UPDATE ... WHERE status = 'pending'` 原子获取任务
3. 处理完成后更新状态

### 2.3 并发控制

- 使用 SQLite 事务保证原子性
- 使用状态字段实现乐观锁
- 支持配置消费者数量

## 3. 与现有系统集成

### 3.1 现有队列系统

当前系统使用 `queue-manager-pro` 库，通过 `MessageQueue` 类实现队列功能。

### 3.2 迁移策略

1. 创建新的基于 SQLite 的队列实现
2. 修改 `queueHandlers.ts` 使用新队列
3. 保留现有 API 接口，确保兼容性

---

## 4. 性能优化考虑

### 4.1 批量操作

- 支持批量入队
- 批量查询待处理任务

### 4.2 索引优化

在 `type` 和 `status` 字段上创建索引，提高查询效率。

### 4.3 清理策略

定期清理已完成的任务，避免表膨胀。

---

## 5. 最佳实践总结

| 实践 | 说明 |
|------|------|
| **队列隔离** | 每种消息类型独立队列 |
| **并行处理** | 同一队列多消费者并行 |
| **持久化** | 使用数据库事务保证可靠性 |
| **监控** | 提供队列状态查询 API |
| **自动清理** | 定期清理历史任务 |
